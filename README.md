## 1. Стек технологий [↑](#содержание)
- **Язык реализации**: Python 3.12.
- **Веб-фреймворк**: Flask 3.x.
- **WSGI-сервер**: Gunicorn 22.x (1 worker, 8 threads).
- **База данных**: SQLite (users.db), модуль sqlite3.
- **Хеширование паролей**: Werkzeug Security (generate_password_hash, check_password_hash).
- **Шаблонизация**: Jinja2, шаблоны хранятся в templates.json и подгружаются через DictLoader.
- **Сеть**: HTTP (порт 5000).
- **Контейнеризация**: Docker, Docker Compose.
- **Тестирование**: Набор чекеров на Python 3 (с использованием `check.py` для интеграции в систему проверки).

## 2. Описание легенды и функционала сервиса [↑](#содержание)
**TXT Cloud** — это веб-сервис для хранения личных `.txt`-файлов. Пользователь регистрируется, входит в аккаунт и может загрузить один текстовый файл размером до 1 Мб. Файл хранится на сервере в директории `storage/{user_id}.txt`. Доступ к файлу имеет только владелец аккаунта. В интерфейсе также есть мини-игра Hyperspace Defender для отвлечения внимания.

### Функционал сервиса:
**1. Регистрация**
- Пользователь вводит логин и пароль.
- Сервис проверяет логин: только буквы, цифры, `-` и `_`, длина до 64; пароль до 128.
- Генерируется уникальный `user_id` (`secrets.token_hex(16)`, 32 hex-символа).
- Выбирается случайный аватар `1.jpg`…`50.jpg`.
- Запись добавляется в SQLite `users`.
- Создаётся пустой файл `storage/{user_id}.txt`.
- Пользователь сразу авторизуется.

**2. Авторизация**
- Пользователь вводит логин и пароль.
- Сервис проверяет хеш пароля в БД.
- При успехе в сессию Flask записывается `user_id`.

**3. Загрузка файла**
- Доступно только авторизованным.
- Принимается только `.txt`, размер не больше 1 Мб.
- Содержимое сохраняется в `storage/{user_id}.txt` (перезапись).
- При превышении размера возвращается 413.

**4. Чтение файла**
- Пользователь открывает `/read`.
- Сервис читает `storage/{user_id}.txt` и отображает содержимое в шаблоне `read_txt.html`.
- В `templates.json` для `read_txt.html` указано `"raw": ["content"]`, и в `html_build.py` содержимое подставляется в шаблон **до** рендеринга Jinja2 (уязвимость).

**5. Просмотр статуса файлов**
- Страница `/files` показывает, загружен ли файл, и даёт ссылки на чтение/замену.

**6. Игра Hyperspace Defender**
- Страница `/game`.
- Canvas-игра, управление `A/D` или `стрелками`, стрельба `SPACE` (пробелом).
- Лидерборд хранится локально в `localStorage` браузера.

**7. Выход из аккаунта**
- Очистка сессии Flask.
- Пользователь возвращается на начальную страницу `/`.

## 3. Описание флагсторов [↑](#содержание)
В сервисе `TXT Cloud` флаг хранится в тексте пользовательского `.txt`-файла.
- **Путь к файлу**: `storage/{user_id}.txt`
- **В контейнере**: `/app/storage/{user_id}.txt`
- **Формат**: флаг записывается как обычная строка, например `TEAM001_XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX` (регулярка в сплойте: `TEAM[0-9]{3}_[A-Z0-9]{32}`).
- **Механизм проверки**:
  1. Чекер регистрирует пользователя.
  2. Загружает `.txt`-файл, содержащий флаг.
  3. Сохраняет `user_id` как `flag_id`.
  4. При проверке логинится под этим пользователем, открывает `/read` и сравнивает содержимое с флагом.
- **Доступ**: флаг защищён логикой сервиса (доступ только владельцу), но уязвим для **SSTI** через загруженный `.txt`.

## 4. Описание уязвимостей [↑](#содержание)
### Уязвимость: Server-Side Template Injection (SSTI)
> **Характеристики уязвимости:**
> - **Название**: Server-Side Template Injection (CWE-1336: Improper Neutralization of Special Elements Used in a Template Engine)
> - **Вектор атаки**: Сетевой (HTTP, через загрузку и чтение `.txt`)
> - **Уровень опасности**: Критический (позволяет прочитать заметки других пользователей)

#### Краткая суть
В `html_build.py` функция `build_page()` сначала подставляет «сырые» значения из `ctx` в исходник шаблона (заменяет `%%content%%` на содержимое файла), и только потом передаёт результат в Jinja2. Если пользователь загрузит `.txt` с Jinja2-выражениями, они будут выполнены на сервере. Это позволяет через `self.__init__.__globals__` добраться до `__builtins__`, импортировать `os` и читать произвольные файлы в `storage/`, включая заметки других пользователей с флагами.

#### Шаги к эксплуатации (на основе sploit.py)
##### 1. Регистрация и авторизация
Сплойт пытается войти под `LOGIN`/`PASSWORD` (по умолчанию `123`/`123`), иначе регистрируется.
##### 2. Загрузка payload
Атакующий записывает на своём устройстве файл `payload.txt`, содержащую следующий фрагмент шаблона **Jinja2** (Python), который используется как эксплойт для **Server-Side Template Injection (SSTI)**:
```Jinja2
{% for f in self.__init__.__globals__.__builtins__.__import__('os').listdir('storage') %}{% if f.endswith('.txt') %}[{{ f }}] {{ self.__init__.__globals__.__builtins__.open('storage/' ~ f).read() }}
{% endif %}{% endfor %}
```
**Разбор по частям:** 
- `{% for f in ... %}` — цикл по файлам.
- `self.__init__.__globals__.__builtins__` — известная цепочка доступа к встроенным функциям Python через объект `self` в Jinja2. Это позволяет выбраться из песочницы шаблонизатора.
- `__import__('os')` — импортирует модуль `os`.
- `.listdir('storage')` — получает список файлов в каталоге `storage`.
- `{% if f.endswith('.txt') %}` — фильтрует только файлы с расширением `.txt`.
- `open('storage/' ~ f).read()` — открывает и читает содержимое каждого такого файла. `~` в Jinja2 — конкатенация строк.
- `[{{ f }}] {{ ... }}` — выводит имя файла в квадратных скобках и его содержимое.

##### 3. Чтение файла
Сплойт открывает `/read`. Сервер рендерит шаблон, и Jinja2 выполняет payload. В ответе оказывается содержимое всех `.txt` в `storage/`.

##### 4. Извлечение флагов
Сплойт ищет флаги регуляркой:
```Python
FLAG_RE = re.compile(r"TEAM[0-9]{3}_[A-Z0-9]{32}")
```
**Важно**: можно заменить на любой другой формат флага для поиска.

##### 5. Сохранение результатов
Найденные флаги дописываются в `flags.txt`.
```Bash
python3 sploit.py
```

#### Инструкция по фиксу
Уязвимость находится в `html_build.py`. Нужно изменить порядок обработки: сначала рендерить Jinja2-шаблон, а затем подставлять «сырые» значения. Смотреть ниже.

##### Было (уязвимый код):
```Python
def build_page(name, **ctx):
    app = current_app
    _ensure_loader(app)

    entry = _REGISTRY[name]
    tpl_src = entry["html"]

    for key in entry.get("raw", ()):
        if key in ctx:
            tpl_src = tpl_src.replace(f"%%{key}%%", str(ctx[key]))

    return app.jinja_env.from_string(tpl_src).render(**ctx)
```

###### Стало (безопасный код):
```Python
def build_page(name, **ctx):
    app = current_app
    _ensure_loader(app)

    entry = _REGISTRY[name]
    tpl_src = entry["html"]

    rendered = app.jinja_env.from_string(tpl_src).render(**ctx)

    for key in entry.get("raw", ()):
        if key in ctx:
            rendered = rendered.replace(f"%%{key}%%", str(ctx[key]))

    return rendered
```
**Пояснение**: Теперь пользовательский контент не попадает в исходник Jinja2-шаблона до рендеринга. Jinja2-выражения в загруженном `.txt` остаются обычным текстом и не выполняются.

## 5. Как деплоить сервисы [↑](#содержание)
Сервис упакован в Docker-контейнер для упрощения развертывания.

### Особенности деплоя
- Нет необходимости в дополнительных системных зависимостях (кроме [Docker](https://www.docker.com/)).
- Flask-приложение запускается через Gunicorn.
- SQLite-БД хранится в томе `txtcloud_data` (`/data/users.db`).
- Загруженные `.txt` хранятся в томе `txtcloud_storage` (`/app/storage`).
- При пересборке без томов данные очищаются.

### Краткое описание развертывания
#### 1. Сборка образа:
```Bash
docker-compose build
```

#### 2. Запуск сервиса:
```Bash
docker-compose up -d
```

#### 3. Проверка работы:
Сервис будет доступен по адресу `http://localhost:5000`.
```Bash
curl http://localhost:5000/
```
### Специфические требования к системе
- **Docker** версии 20.10+.
- **Docker Compose** версии 2.0+.
- Доступный порт **5000** на хост-машине.
- 100 МБ свободного места для образов и данных.

## 6. Как деплоить чекеры [↑](#содержание)
Чекеры предназначены для валидации работоспособности сервиса и проверки сохранности флагов в системе A&D (Attack & Defense).

### Особенности деплоя
- Чекеры написаны на Python 3.
- Используют зависимости из `requirements.txt` (например, `requests`).
- Взаимодействуют с сервисом по HTTP.
- Конфигурация сервиса описана в `services.yml` как `txt_cloud`.

### Краткое описание развертывания
#### 1. Установка прав на выполнение:
```Bash
chmod +x checkers/txt_cloud/checker.py
```

#### 2. Установка зависимостей чекера:
```Bash
pip install --break-system-packages -r checkers/txt_cloud/requirements.txt
```

#### 3. Локальное тестирование сервиса через `checker.py`:
Перейдите в директорию `./checkers/txt_cloud/`:
```Bash
DEBUG=true python3 checker.py check localhost --debug
```

#### 4. Запуск валидации через `check.py`:
Система валидации использует скрипт check.py из корня репозитория. Для запуска проверки выполните:
```Bash
export SERVICE=txt_cloud
./check.py up
./check.py check
```
**Примечание**: Эта команда автоматически поднимет контейнеры (если они не запущены) и выполнит полный цикл тестов: регистрация, загрузка, чтение, проверка флага.

#### 5. (Бонус) Дополнительно тестирование сервиса через `test.py`:
Установка прав на выполнение:
```Bash
chmod +x checkers/txt_cloud/test.py
```
Режимы запуска:
1. Тестирование с использованием `star_wars_messages.json` (случайное сообщение)
```Bash
python3 test.py
```
2. Тестирование с генерированным флагом вида `TEAM000_XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX`
